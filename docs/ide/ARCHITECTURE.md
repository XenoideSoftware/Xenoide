
# Xenoide Architecture

## Domain Model

Check the @DOMAIN-MODEL.md document.

## Non-functional Requirements
- **Composable** and **Extensible**: Allows to implement new services and features by composing existing services and adapting external ones.
- **Testable**: Hexagonal Architecture will be leveraged to abstract away UIs and external IO in order to get a testable codebase. UI logic and IO orchestration will be tested as well.

## Platform Support

### Primary support

Cross-platform support with two tiers:

- **Windows 10/11**
- **Linux / GTK**
- **macOS / AppKit** (via Objective-C++ interop).

## Infrastructure
Multi-process, hexagonal architecture, event-oriented, modular, extensible, desktop application.

- **Hybrid concurrency**: Some services run as worker threads, part of the main process, and other services run as separate processes. From the core's point of view there is no difference: any interaction is by means of async calls.
- **Event oriented**: Application events that are generated by either the User or external processes trigger an internal event / message processing, which is handled by the central EventBus, which in turn broadcasts to all interested internal components for background processing. This will increase application responsiveness and performance, and give monitoring and logs essentially *for free*.


## Native UI Architecture
- **Passive Model View Presenter**: UI logic will be decoupled using the Passive-View variant of the Model View Presenter architectural pattern. This will allow to implement multiple native UIs with less effort. UIs will *react* to application events, notified by the Presenter via the abstract View. Native UI will translate native events to application events and then notify the Presenter. All of these notifications will be completely *async*. There will be some UI components that are essentially groups for other components (think of a Document / Editor component) in a tabbed MDI application, or might have multiple views (an XML code editor and a view that displays the XML tree as a graph).
- **UI Main Process Thread**: The UI main thread will own the OS event processing, and will instantiate the application core along with all required dependencies, injecting specific component implementation based on configuration, project characteristics, among others. In other words, the main UI process becomes the orchestrator (using prebuilt functionality from the application cross-platform core).
- **Native UI Toolkit**: We will use the native UI toolkit for each platform to achieve the highest level possible of integration with the underlying operating system.

## Hexagonal Architecture
Entities are located relative to the hexagon using hexagonal terms:

- **Primary ports**: the driving side, where the UI connects to the core.
- **Secondary ports**: the driven side, where the core reaches out to external services.
- **Core**: an alias for the "application cross-platform core", which constitutes the EventBus (for now).

## Architectural Archetypes
As we will create several instances of modules that will share some common characteristics, we will group them in the following archetypes:

- **Event** (abstract base): Indicates that a stimulus was applied to the system that must be processed.
  - **Action**: An application-level event that was triggered by the user, or must be manifested at the UI layer.
  - **Message**: A system/background-level event that was triggered by either some application event or some external system, and must be processed. Eventually, as part of the processing, might trigger other **Actions** or **Messages**.
- **Component**: An entity that can run in a separate thread, and can receive and emit events. Additionally, based on those events, it can generate **Actions** that will end in the native UI, which will update the user interface. Internally, a Component holds an abstract **View** and a **Presenter**, and it is the **Presenter** that processes / emits the events.
  - **View**: the entity that connects with the concrete user interface.
  - **Presenter**: orchestrates between the view(s) and the Model. An alias is **Orchestrator**.
- **Service**: An entity that runs in either a separate thread or a separate process. It can receive and emit events.

In MVP terms, the **Model** is just a way to name a set of **Services** the Presenter might interact with.

The central transport is the **EventBus**, which carries all **Event** subtypes (both **Action** and **Message**).

Features must be specified by specifying one or more of the concrete archetypes (Action, Message, Component, Service, and the sub-archetypes of Component).

## Known Gaps and Issues

The following issues were identified during review. They are grouped by category and ordered roughly by severity. Each entry is a gap in this document to be resolved in a future revision.

### 1. Missing domain model (the "empty hexagon")

1. **The core has no domain.** The document reduces `Core` to the EventBus (a transport), but hexagonal architecture requires the core to hold use cases and domain entities (documents, buffers, projects, workspaces, symbols/index, diagnostics, debug sessions, commands). Without a domain model the core routes events into an empty box.
2. **The `Model` is undefined.** Stating that the Model is "just a set of Services" (line 48) leaves the actual heart of an IDE undescribed.

### 2. Messaging / event-model gaps

3. **No request/response primitive.** The taxonomy has only `Action` and `Message` (both fire-and-forget). There is no Query/Command/Reply, no correlation ID, no Future/Promise. Presenters cannot await a result (e.g., fetching directory children for a TreeView, stepping a debugger, requesting completions).
4. **`Action` vs `Message` collapses.** `Action` mixes two unrelated criteria (origin: user-triggered; destination: manifested at UI), and a `Message` may emit further `Action`s or `Message`s. Both can emit both, so the distinction is meaningless.
5. **No ordering/causality guarantees.** Sequence numbers, causal delivery, and idempotency are unspecified (e.g., a "file-deleted" event arriving before "file-created").
6. **No cancellation or progress model.** Long-running operations (find-in-files, build, indexing, type-ahead completion) need cancellation tokens, progress reporting, and streaming results.

### 3. Concurrency / process gaps

7. **Threads and processes are not equivalent.** The claim that a thread and a process are indistinguishable from the core's point of view is false: they differ in failure modes, serialization costs, memory sharing, and ordering semantics.
8. **No lifecycle / supervision model.** Who starts and stops Components and Services, how shutdown is ordered (e.g., flush buffers before exit), and what happens when a Service crashes or a process dies are unspecified.
9. **No failure/error channel.** Events are fire-and-forget; there is no supervision, restart, health-check, dead-letter queue, or error delivery path.

### 4. Use-case gaps

10. **Remote development is absent.** No wire protocol, event serialization/versioning, local-vs-remote backend abstraction, latency/partial-failure/reconnection semantics, or credential/session/identity model.
11. **Sync / initial-load flows are unsupported.** The "all async" mandate provides no mechanism for a synchronous-looking fetch, no incremental/delta update, and no pagination for large collections.
12. **Plugin system is underspecified.** No plugin interface (Component vs Service), no registration/routing rules, no lifecycle (load/unload/reload), no isolation boundary (process vs thread), no extension-point catalog, no service discovery/DI, and no native-UI contribution story.
13. **Debugging and refactoring are unrepresentable.** Debugging needs stateful sessions and bidirectional request/response; refactoring needs a workspace model, an index, a transactional multi-file edit/undo abstraction, and dirty-buffer handling. None exist.

### 5. MVP / UI gaps

14. **View/Presenter cardinality is contradictory.** A Component "holds an abstract View and a Presenter" (1:1), but the text also describes a Document with multiple views (e.g., XML text + graph).
15. **Passive-View + all-async is unresolved.** With fully async notifications, it is unspecified who holds intermediate state while awaiting a result and how the async continuation reaches the Presenter.
16. **Native UI scope is underexamined.** Three full native UIs (Win32, GTK, AppKit via ObjC++) are committed to with no feasibility mitigation.

### 6. Documentation / scope gaps

17. **Contradictory definitions.** `Core` is simultaneously the EventBus and the application core; Component and Service overlap (both can run in a thread).
18. **No diagrams.** A hexagonal architecture described only in prose lacks the hexagon, component/deployment, and sequence diagrams needed to make port/component boundaries unambiguous.
19. **No non-functional requirements.** Responsiveness/performance are asserted without latency budgets, startup targets, memory caps, or acceptance criteria.
20. **No test strategy.** "Testable" is asserted without describing how async event flows, multi-process services, or native presenters are tested.
21. **Scope red flag: Legacy Windows 9x.** Best-effort support for Windows 9x is incoherent for a modern IDE (predates the "primary" 10/11 tier; no modern toolchain targets it).
