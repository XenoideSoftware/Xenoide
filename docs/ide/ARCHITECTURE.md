
# Xenoide Architecture

## Platform Support 

Insane level cross-platform support

- Windows 9x series
- Windows 10x series
- Linux / GTK 
- macOS / UIKit (via ObjectiveC++ interop).

## Core Architecture
Multi-process, layered, hexagonal architecuture, event-oriented, modular, extensible, desktop application.

- **Multi-process**: Increases stability and UX responsiveness. Paves the way to implement remote development, pair programming, and other advanced features.
- **Multi-threaded**: Some services might benefit from being executed as another thread, part of the application's main thread. Some uses case: to quicly access / process a shared memory block.
- **Event oriented**: Application events that are generated by either the User or external processes triggers an internal event / message processing, which are by a central message bus, which in turn will broadcast to all interested internal components for background processing. This will increase application responsiveness and performance, and give monitoring and logs essentially *for free*.
- **Composable** and **Extensible**: Allows to implement new services and features by composing existing services and adapting external services.
- **Testable**: Hexagonal Architecture will be leveraged to abstract away UIs and external IO in order to get a testable codebase. UI logic and IO orchestration will be tested as well.

## Native Application Architecture
- **Passive Model View Presenter**: UI logic will be decoupled from the using the Passive-View variant of the Model View Presenter architectural pattern. This will allow to implement multiple native UIs with less effort. UIs will *react* to application events, notified by the Presenter via the abstract View. Native UI will translate native events to application events and then notify to the Presenter. All of these notifications will be completely *async*. There will be some UI components that are essentially groups for others components (think of a Document / Editor component) in a tabbed MDI application, or might have multiple views (an XML code editor and a view that displays the XML tree as a graph).
- **UI Main Process Thread**: The UI main thread will own the OS event processing, and will instanciate the application core along all required dependencies, injecting specific component implementation based on configuration, project characteristics, among others. In other words, the main UI process becomes the orchestrator (using prebuilt functionality from the application cross-platform core).
- **Native UI Toolkit**: We will use the native UI toolkit for each platform to achieve the highest level possible of integration with the underlying operating system.

## Architectural Archetypes
As we will create several instances of modules that will share some common characteristics, we will group them in the following archetypes:

- **Event**: Indicates that a stimilus was applied to the system that must be processed.
- **Action**: An application event that was triggered by the user, or must be manifested at the UI layer. 
- **Message**: A system event that was triggered by either some application event or some external system, and must be processed. Eventually, as part of the processing, might trigger other **Actions** or **Messages**.
- **Component**: An event emitter and / or receiver which does have an associated user interface port.
- **Service**: An event emitter  and / or receiver which runs in the background.

Features must be specified by specifying one or more of previous archtypes.
