# Xenoide Architecture

Architectural patterns and archetypes used across the IDE and related applications. The domain model lives in @DOMAIN-MODEL.md; the domain vocabulary is defined in @GLOSSARY.md.

## Non-functional Requirements

- **Composable** and **Extensible**: implement new services and features by composing existing services and adapting external ones.
- **Testable**: hexagonal architecture abstracts away UIs and external I/O for a testable codebase. UI logic and I/O orchestration are tested as well.

## Platform Support

Cross-platform support with two tiers:

- **Windows 10/11**
- **Linux / GTK**
- **macOS / AppKit** (via Objective-C++ interop)

## Infrastructure

Multi-process, hexagonal, event-oriented, modular, extensible desktop application.

- **Hybrid concurrency**: some services run as worker threads in the main process, others as separate processes. From the core's point of view, interaction is always by means of async calls.
- **Event-oriented**: application events generated by the User or external processes trigger internal message processing handled by the central **EventBus**, which broadcasts to all interested components. This improves responsiveness and gives monitoring and logging essentially for free.

## Native UI Architecture

- **Passive Model-View-Presenter**: UI logic is decoupled using the Passive-View variant of MVP. UIs react to events notified by the Presenter via the abstract View; native UI translates native events to application events and notifies the Presenter. Notifications are async. A Document / Editor component may have multiple views (e.g. an XML code editor and a view that shows the XML tree as a graph).
- **UI Main Process Thread**: the UI main thread owns OS event processing and instantiates the application core, injecting implementations based on configuration and project characteristics.
- **Native UI Toolkit**: use the native toolkit per platform for maximum OS integration.

## Hexagonal Architecture

- **Primary ports**: the driving side, where the UI connects to the core.
- **Secondary ports**: the driven side, where the core reaches out to external services (Tools).
- **Core**: the application cross-platform core, holding the domain model (@DOMAIN-MODEL.md) and its use cases. 

## Architectural Archetypes

### Messages (the bus)

- **Message** (abstract base): a unit of information carried by the EventBus.
  - **Command**: an imperative instruction sent *to* a service, consumed by exactly one handler (PUSH/PULL). Emitted by an Action or programmatically. Mirrors the domain **Command**.
  - **Event**: a declarative announcement broadcast by a service to all subscribers (PUB/SUB). Mirrors the domain **Event**. No Action maps to an Event directly.

### Presentation

- **Action**: a UI-layer object bridging user intent and Commands. Has a visual representation (menu item, toolbar button, keybinding), an enabled/disabled state driven by the application state machine, and emits exactly one Command when activated. Actions are registered in an **ActionRegistry**, which observes state transitions and enables/disables Actions in bulk.
- **View**: the entity connecting to the concrete user interface.
- **Presenter** (alias **Orchestrator**): orchestrates between the View(s) and the domain; processes and emits events.

### Runtime

- **Component**: an entity that can run in a separate thread and can receive and emit messages. Holds an abstract **View** and a **Presenter**; the Presenter processes/emits the messages.
- **Service**: an entity that runs in a separate thread or process and can receive and emit messages.

### Composition

- **Feature**: a bundle of UI components + Services + Commands delivering a workflow. Its domain-level meaning is captured by **Command** and **Tool Capability**; Feature is an architecture-level composition unit.
- **Plugin**: a deployment/extension unit contributing Features, Tools, and UI, with an install/uninstall lifecycle.

In MVP terms, the **Model** is the domain model (plus the Services a Presenter interacts with).

Features are specified by naming the concrete archetypes they compose (Commands, Events, Actions, Components, Services).
